# PRD — ออกแบบฐานข้อมูลระดับเอนเตอร์ไพรส์ (รอบ system กลางก่อน)

- สถานะ: rev 3 รอ review (ห้ามลงโค้ดจนกว่า operator ยืนยัน) — rev 1 โดน NOT READY 1 เต็ม 10, rev 2 ส่งตรวจคู่แต่ reviewer ติด timeout สองรอบ gate จึงยังปิดอยู่
- Branch: `feat/enterprise-db-design` (แตกจากงาน pi รวม import pipeline)
- วันที่: 11 ต.ค. 2569

## 1. ปัญหาและความต้องการ

ระบบปัจจุบันตั้งค่าได้เฉพาะบางจุด (บอท หน่วยงาน หมวด ผู้ใช้ ผู้รับผิดชอบ) ส่วนกลางยังไม่มี ตาราง system กลางไม่มี สวิตช์ฟิลด์รายกลุ่มไม่มี สิทธิ์กลุ่มย่อยไม่มี การตั้งค่า API กระจายใน env และการให้โมเดล (MCP) เข้ามาช่วยยังไม่มีขอบเขตชัด งานนี้ต้องการฐานที่ตั้งค่าได้ครบทุกจุด ยืดหยุ่น และเผื่อขยายเป็นหลายหน่วยงาน

## 2. ขอบเขต (ตามคำตอบ operator)

- เริ่มที่ตาราง system กลางก่อน แล้วค่อยสวิตช์ฟิลด์และสิทธิ์ (operator เลือก system กลางก่อน)
- เผื่อสเกลหลายหน่วยงาน (หลาย อบต. หรือเทศบาล เรื่องระดับหลักแสน)
- MCP ทั้งอ่านและสั่งงาน (ไม่ใช่แค่อ่าน)

### In (รอบนี้)

1. ตาราง `system_settings` กลางแบบ key คู่ value พร้อมหน้า admin สำหรับ head ขึ้นไป
2. แนวทาง multi-org: ทุกตารางหลักมี `org_id` (เริ่มใช้ค่าเดียว `huangua` ระบบเดิมทำงานเหมือนเดิม)
3. log audit และ health ให้ครบ: ใช้ `audit_logs` เดิมต่อ บวก cron ลบ log เกิน `audit_retention_days` (ค่าเริ่ม 365 วัน ตอบแค่จำนวนแถว) และ route health ฐานข้อมูลแบบ public
4. ตารางตั้งค่า API กลาง: provider มีแค่ `line` `s3` `smtp` สถานะมีแค่ `unknown` `connected` `degraded` `down` เก็บแค่ปลายทางกับสถานะ ปุ่ม refresh เขียนสถานะกับเวลาตรวจใหม่พร้อม audit ไม่เก็บ secret ดิบ (secret อยู่ใน env ต่อไป)
5. ขอบเขต MCP รอบนี้: รีจิสทรีในโค้ดก่อน (ยังไม่เปิด HTTP): tool อ่านต้อง `STAFF_ROLES` action เขียนต้อง `CASE_SUPERVISOR_ROLES` เครื่องมือแอดมินต้อง `ADMIN_ROLES` ไม่รู้จักปฏิเสธก่อนเสมอ

### Out (ยังไม่ทำรอบนี้)

- สวิตช์ฟิลด์รายกลุ่ม (รอบถัดไป)
- สิทธิ์กลุ่มย่อยใต้หน่วยงาน (รอบถัดไป)
- การแยกฐานจริงเป็นหลาย DB (รอบนี้แค่เผื่อคอลัมน์และ index)

## 3. เกณฑ์ยอมรับ (พิสูจน์ได้)

- มี migration สร้างตารางใหม่และรันบน DB ทดสอบ local ผ่าน
- หน้า settings กลางบันทึกค่าได้และมี audit ทุกครั้งที่เปลี่ยน
- ฟอร์มเดิมทำงานเหมือนเดิมเมื่อ `org_id` เป็นค่าเดียว (test เดิมเขียว)
- cron ลบ log เก่าทำงานและตอบแค่จำนวนแถว
- ปุ่ม refresh ของ API เขียนสถานะใหม่พร้อม audit
- health check ฐานข้อมูลตอบได้ (connected latency tables count)
- MCP เรียกได้เฉพาะ tool ที่อนุญาต และ action ที่เกินสิทธิ์ถูกปฏิเสธพร้อม audit

## 4. ข้อจำกัด

- ห้ามพิมพ์ PII ดิบใน log และ output (พิมพ์ได้แค่ hash จำนวน เลขแถว)
- staging และข้อมูลจริงอยู่ใต้ `secrets/` เท่านั้น
- ห้ามแตะ production ทุกขั้น ทดสอบบน local เท่านั้น
- ใช้ `npx` ห้าม `pnpm`
- migration ที่แก้ enum ต้องรันนอก transaction (บทเรียนจาก 0014)

## 5. ตัวชี้วัดความสำเร็จ

- ตั้งค่าครบทุกจุดที่รอบนี้สัญญาโดยไม่แก้โค้ด
- test ใหม่และเก่าผ่านทั้งหมดบน local
- dry-run นำเข้ายังผ่าน 270 แถวเหมือนเดิม
- operator ที่ไม่ใช่ dev ใช้งานหน้าตั้งค่าได้โดยไม่งง
