# เอกสารส่งต่อ: ผลตรวจ UX/UI และแนวทางปรับปรุงระบบ อบต.หัวงัว

วันที่จัดทำ: 25 ตุลาคม 2026
สถานะ: สรุปบทสนทนาและผลตรวจเดิม พร้อมข้อจำกัดการดำเนินงาน ไม่ใช่รายงานรับรองว่าทุกหน้าผ่านการทดสอบแล้ว
กลุ่มผู้อ่าน: เอเจนต์พัฒนา ผู้พัฒนา ผู้ตรวจงาน และเจ้าของระบบ

> **อ่านก่อนทำงาน: ผู้ใช้พอใจกับ Landing page `/` แล้ว ห้ามรีดีไซน์หรือเปลี่ยนหน้าแรกทั้งทางตรงและทางอ้อมโดยไม่ได้รับอนุมัติใหม่อย่างชัดเจน งานนี้ไม่ใช่คำสั่งอนุมัติให้ลงมือแก้ทุกข้อในรายงาน**

> **หมายเหตุสถานะปัจจุบัน: ยังไม่ได้แก้ไขหน้าอินเดกซ์ (หน้าแรก `/`) จากการจัดทำเอกสารนี้ และยังไม่ให้แตะหน้าอินเดกซ์ในงานปรับ UX/UI รอบถัดไป ให้คงดีไซน์เดิมไว้ก่อน หากจะปรับในอนาคตต้องขออนุมัติจากผู้ใช้ใหม่เป็นงานแยก**

## 1. ข้อตกลงกับผู้ใช้และขอบเขต

- รักษา Landing page เดิม ทั้งโครงหน้า สี ฟอนต์ รูป ข้อความ ระยะห่าง Responsive และแอนิเมชัน
- แนวทางปรับดีไซน์เน้นหลังบ้าน `/admin` และเส้นทางย่อย เป็นการเก็บรายละเอียด ไม่ใช่รีดีไซน์ทั้งเว็บ
- **ทุกหน้าในแอดมินต้องคุมโทนจากหน้าอินเดกซ์ `/` ที่ผู้ใช้อนุมัติแล้ว** ให้หน้าแรกเป็นต้นแบบด้านอัตลักษณ์ สีหลัก ฟอนต์ รูปแบบปุ่ม มุมโค้ง และน้ำหนักภาพรวม เพื่อให้รู้สึกว่าเป็นระบบเดียวกัน ไม่สร้างธีมแอดมินที่แยกขาดหรือขัดกับหน้าแรก
- ยึดอัตลักษณ์หน้าแรก ไม่ใช่คัดลอกโครง Landing page มาใช้กับหน้าทำงาน: ตาราง ฟอร์ม เมนู และรายละเอียดเรื่องปรับให้เหมาะกับงานแอดมินและ Accessibility ได้ โดยยังคงโทนเดียวกัน
- ให้ปรับแอดมินเข้าหาดีไซน์หน้าแรกเท่านั้น ไม่ย้อนกลับไปแก้หน้าแรกเพื่อให้เข้ากับแอดมิน การแยก CSS/Tokens เป็นการแยกขอบเขตผลกระทบทางเทคนิค ไม่ใช่การอนุญาตให้เปลี่ยนอัตลักษณ์
- ผลตรวจ `/intake` และ `/track` เป็นรายการงานแยก ต้องได้รับมอบหมายก่อนแก้ ไม่ขยายขอบเขตจากงานแอดมินไปหน้าสาธารณะเอง
- แก้ข้อผิดพลาดที่กระทบงาน ความปลอดภัย และข้อมูลก่อนเพิ่มความสวยหรือเอฟเฟกต์
- ข้อเสนอ Design System และ Motion เป็นทิศทางที่แนะนำ ยังไม่ใช่การอนุมัติเปลี่ยนสไตล์จริง
- ใช้ UI copy และคำศัพท์โดเมนภาษาไทย

## 2. Protected Design: ห้ามกระทบหน้าแรก

### 2.1 ข้อห้าม

1. ห้ามแก้ดีไซน์หรือพฤติกรรม `/` โดยตรง รวมถึงบนมือถือและเดสก์ท็อป
2. ห้ามแก้ไฟล์ร่วมจนทำให้หน้าแรกเปลี่ยน แม้ไฟล์หน้าแรกไม่ได้อยู่ใน Diff
3. ห้ามเพิ่ม Global CSS, เปลี่ยน Theme, ฟอนต์, CSS reset, Design tokens หรือค่าเริ่มต้นของ Shared UI เพื่อแก้แอดมินแบบครอบทั้งเว็บ
4. ห้ามนำแนวทางลด Gradient/Glass/Animation ของแอดมินไปลบลูกเล่นเดิมของ Landing page
5. ห้ามลบ LIFF redirect, เปลี่ยนลิงก์หรือข้อมูลจริงของหน้าแรกเพื่อให้ทดสอบง่ายขึ้น
6. ถ้าจำเป็นต้องแตะส่วนที่ป้องกัน ให้หยุด อธิบายไฟล์ ผลกระทบ และทางเลือก แล้วขออนุมัติเจาะจงก่อน

### 2.2 ไฟล์ที่ยืนยันจากโค้ดในการจัดทำเอกสาร

ไฟล์หน้าแรกและคอมโพเนนต์โดยตรง:

- `src/components/landing/Navbar.tsx`

- `src/components/landing/Stats.tsx`
- `src/components/landing/stats-client.tsx`

- `src/components/landing/HowItWorks.tsx`

ไฟล์ร่วมที่มีผลต่อหน้าแรก ต้องไม่แก้ในงานแอดมินโดยไม่มีการอนุมัติผลกระทบ:

- `src/app/layout.tsx` — ฟอนต์ Noto Sans Thai, โครง HTML, Theme และ Metadata
- `src/styles/tokens.css` — Global styles และ Design tokens ที่ Root layout นำเข้า
- `src/components/ui/button.tsx` — Navbar, Hero และ CTA ใช้ร่วม

- `src/components/liff/liff-state-redirect.tsx` — เส้นทางเข้าจาก LIFF

นี่เป็นรายการจุดเริ่มต้น ไม่ใช่ Dependency/asset inventory ที่ครบถ้วนทุกระดับ ก่อนแก้ต้องตรวจ imports ต่อเนื่องและ assets ที่เกี่ยวข้องเพิ่มเติม ห้ามสร��ปว่าไฟล์นอกลิสต์ปลอดภัยโดยอัตโนมัติ

หน้าแรกมีสถิติจากฐานข้อมูลและปีงบประมาณที่เปลี่ยนตามเวลา การทดสอบภาพต้องควบคุมข้อมูล/เวลาในระบบทดสอบ ไม่แก้ Production code ให้ข้อมูลตายตัว

### 2.3 วิธีแยกงานแอดมิน

- ใช้ CSS scope ภายใน Wrapper ของแอดมิน และตัวแปรที่ประกาศเฉพาะขอบเขตนั้น
- ตรวจ DOM/Portal ของ Dialog และ Tooltip ด้วย เพราะ Portal อาจออกนอก Wrapper แล้วไม่ได้รับ scoped tokens
- ใช้ Adapter/Variant เฉพาะแอดมินเมื่อจำเป็น แทนเปลี่ยนค่าเริ่มต้นของปุ่มที่ Landing ใช้
- ห้ามเพิ่ม Dependencies หรือเปลี่ยน Global provider โดยไม่ประเมิน Bundle และผลกระทบต่อหน้าสาธารณะ
- ตรวจ caller ของคอมโพเนนต์ก่อนปรับ ไม่เดาจากชื่อไฟล์

### 2.4 ด่านตรวจป้องกัน

- เก็บภาพก่อนเริ่มจากเวอร์ชันที่ผู้ใช้ยอมรับ พร้อม commit, URL, viewport, theme และข้อมูลทดสอบ
- เปรียบเทียบอย่างน้อยมือถือและเดสก์ท็อป ครอบคลุมทุก Theme ที่รองรับจริง
- ทดสอบเมนู ลิงก์หลัก การเข้า LIFF และ Responsive ของหน้าแรก
- ตรวจ Diff ทั้งไฟล์ตรงและไฟล์ร่วม ไม่พึ่งภาพเพียงอย่างเดียว
- หากเพิ่ม Visual regression test ให้ทดสอบว่าการแก้สไตล์จงใจทำให้ Gate ล้มเหลวจริงก่อนอ้างว่าเป็นการป้องกัน
- ห้ามปรับ Baseline เพื่อกลบ Regression โดยไม่อนุมัติ
- เอกสารและกติกาไม่ใช่ Technical enforcement: ในรอบนี้ยังไม่ได้ติดตั้ง Visual regression gate หรือ Branch protection
- ถ้า Browser/ฐานข้อมูลไม่พร้อม ให้รายงานว่า “ยังย���นยันหน้าแรกไม่เปลี่ยนไม่ได้” ห้ามอ้างว่าผ่าน และไม่ควร Merge งาน UI จนตรวจได้

## 3. หลักฐานและสถานะการตรวจ

- บทสนทนาก่อนหน้าระบุการสำรวจ 39 เส้นทางแอดมิน และตรวจโค้ดเพิ่มเติมในเส้นทางรับเรื่องถึงปิดเรื่อง
- ข้อค้นพบส่วนใหญ่เป็น Static review ไม่ใช่ผลทดสอบด้วย Browser ทุกหน้า
- การทดสอบหลังเข้าสู่ระบบในรอบก่อนมีข้อจำกัด Preview/การเชื่อมต่อฐานข้อมูลและ Redis นั่นเป็นสถานะในเวลานั้น ไม่ใช่หลักฐานว่า Environment ปัจจุบันยังเสีย
- เลขบรรทัดจากรายงานเก่าอาจเลื่อน เอกสารนี้อ้างพาธเป็นจุดเริ่มต้น ให้ยืนยันพฤติกรรมปัจจุบันก่อนแก้
- “ความเสี่ยง” ต้องทำ Reproduction/ทดสอบก่อนเรียกว่า Bug ยืนยันแล้ว
- การทำเอกสารรอบนี้ตรวจพาธหน้าแรกและ Imports โดยตรงใหม่ แต่ไม่ได้ตรวจทุกข้อค้นพบซ้ำ

### สิ่งที่เคยแก้แล้วตามบทสนทนา

- หน้า Login ได้รับการปรับเพื่อรับมือ Hydration mismatch จาก LastPass โดยยังรองรับ Autofill
- รายงานเดิมระบุว่า ESLint และเทสต์ Hydration ที่เกี่ยวข้องผ่านในรอบนั้น แต่ยังไม่ได้ยืนยัน Preview จริง
- ต้องตรวจ Git diff/ประวัติและทดสอบปัจจุบันก่อนอ้างว่างานนั้นยังคงอยู่และไม่มี Regression

### สิ่งที่ยังไม่ถือว่าทำแล้ว

- รายการปรับ UX/UI ด้านล่างส่วนใหญ่ยังเป็นข้อเสนอ/ผลตรวจ ไม่ใช่งานที่แก้เสร็จ
- ยังไม่มีผลวัด Web Vitals จริงสำหรับประเด็นประสิทธิภาพในรายงาน
- ยังไม่มีหลักฐานทดสอบมือถือ คีย์บอร์ด Screen reader และทุกบทบาทครบเส้นทาง

## 4. ผลตรวจรวมและลำดับความสำคัญ

P1 = เสี่ยงต่อคำสั่งจริง การทำงานต่อไม่ได้ หรือการเข้าถึงหลัก ควรแก้ก่อนใช้งานจริง
P2 = ควรแก้ลำดับถัดไปเพื่อลดความผิดพลาดและความสับสน
P3 = ปรับความสม่ำเสมอและประสบการณ์หลังแก้ปัญหาหลัก
ลำดับนี้เป็นการจัดความสำคัญเพื่อส่งต่อ ไม่ใช่คะแนนจากการทดสอบผู้ใช้

## 5. แนวทางความสวยงามและ Design System

ทิศทางที่เสนอ: **ราชการที่ทันสมัย เป็นมิตร อ่านง่าย** ไม่ใช่รีดีไซน์ Landing page

### 5.1 ภาพรวมแอดมิน

- สีน้ำเงินเดิม พื้นผิวอ่านง่าย แยกส่วนด้วยระยะห่างมากกว่าเส้นขอบหรือเงาหนัก
- ลำดับตัวอักษร: ชื่อหน้า → หัวข้อส่วน → เนื้อหา → ข้อมูลประกอบ รองรับวรรณยุกต์ไทย
- มีปุ่มหลักเด่นหนึ่งคำสั่งต่อบริบท คำสั่งรอง Outline/Ghost และคำสั่งเสี่ยงแยกให้ชัด
- ลดจำนวนระดับ Radius/Shadow ใช้ไอคอนสม่ำเสมอ ไม่เพิ่มฟอนต์โดยไม่จำเป็น
- ตารางตัวเลขชิดขวา สถานะอ่านเร็ว Hover/Focus row ไม่ทำให้เข้าใจว่าแถวกดได้ถ้ากดไม่ได้
- Signature element ที่เสนอคือ Timeline เรื่อง: เห็นถึงขั้นไหน ใครรับผิดชอบ และทำอะไรต่อ

### 5.2 Motion และเอฟเฟกต์

| จุด | แนวทางเสนอ |
|---|---|
| ปุ่ม/ขอบ/สี | Transition ประมาณ 120–160ms ไม่ทำให้ Layout ขยับ |
| Drawer/Dialog | Fade และเลื่อนสั้นประมาณ 180–240ms พร้อม Focus management |
| บันทึก | Pending → ผลลัพธ์ ปุ่มขนาดไม่กระโดด ป้องกันกดซ้ำ |
| เปลี่ยนสถานะ | Highlight สิ่งที่เปลี่ยนชั่วครู่ ไม่ Animate ทั้งหน้า |
| โหลด | Skeleton ขนาดใกล้เนื้อหาจริงและมีสถานะสำหรับ Screen reader |
| Validation | Error ใกล้ช่องและโฟกัสที่เหมาะสม ไม่ใช้เอฟเฟกต์สั่น |

- ตัวเลขเวลาเป็นแนวทางเสนอ ยังไม่ใช่ค่าที่ติดตั้งแล้ว
- ใช้ opacity/transform เป็นหลัก ไม่ทำให้การทำงานช้าลง
- รองรับ `prefers-reduced-motion` และยังสื่อผลครบเม���่อปิด Motion
- ใช้ Focus ring, เงาบางเฉพาะส่วนลอย, Highlight ผลค้นหา/รายการอัปเดต และ Tooltip สำหรับข้อมูลเสริม
- หลีกเลี่ยง Glassmorphism ทั่วแอดมิน, Gradient หนัก, Glow, Parallax, Background เคลื่อนไหว, ตัวเลขวิ่งทุกครั้ง, Hover ยกการ์ดที่กดไม่ได้ และ Confetti ในงานร้องทุกข์
- ข้อแนะนำหลีกเลี่ยงเอฟเฟกต์ไม่ใช่คำสั่งให้ลบเอฟเฟกต์ Landing เดิม

### 5.3 โครงสร้าง Design System ที่เสนอ

1. Foundations: Semantic colors, Typography, Spacing, Radius, Shadow, Icon sizes และ Motion tokens แบบ scoped admin
2. Components: Button, Field, Select, Badge, Alert, Dialog, Table, Pagination และ Skeleton
3. Patterns: บันทึกฟอร์ม, ยืนยันคำสั่งเสี่ยง, ตัวกรอง, อัปโหลด และกู้ค��น Error

ใช้ Storybook ที่มีตามข้อมูลโครงการเป็นแค็ตตาล็อกจริง ตรวจ Setup ก่อนใช้ ไม่ติดตั้ง Library ใหม่โดยไ���่มีเหตุผล ทุกคอมโพเนนต์ต้องมี Default/Focus/Disabled/Loading/Error/Success รวมทั้งข้อความไทยยาวและมือถือ

## 7. PRD สำหรับงานส่งต่อ

### ปัญหาและความต้องการ

เจ้าหน้าที่ต้องทำงานได้ถูกต้อง เห็นผลคำสั่ง ไม่เสียค่าฟอร์ม ใช้มือถือ/คีย์บอร์ดได้ และพบ UI ที่สม่ำเสมอ ขณะเดียวกันผู้ใช้ไม่ต้องการให้หน้าแรกที่อนุมัติแล้วเปลี่ยน

### ขอบเขต

- เอกสารนี้รวบรวมผลตรวจ ความเสี่ยง ลำดับงาน เกณฑ์ผ่าน และข้อห้าม
- การพัฒนารอบถัดไปเลือกเฉพาะรหัสงานที่ได้รับมอบหมายเป็น Tranche
- ไม่รวมการรีดีไซน์หน้าสาธารณะ เปลี่ยน Stack/Auth ย้ายฐานข้อมูล หรือเปลี่ยน Lifecycle โดยอัตโนมัติ

### เกณฑ์ยอมรับและตัวชี้วัด

- ไม่มี Diff ในส่วนป้องกันที่ไม่ได้รับอนุมัติ และหน้าแรกผ่านการเปรียบเทียบก่อน–หลัง
- ทุก Mutation ใน Tranche ที่รับทำมี Pending/Success/Error และไม่เกิดการกดซ้ำโดยไม่ตั้งใจ
- สถานะ Draft/Scheduled/Sent ตรงกับปุ่มและผลจริง
- งานที่เกี่ยวข้องผ่าน Role matrix, Keyboard, Mobile และ Error recovery ตาม Test plan
- ไม่มีข้อมูลค้างหายเงียบในสถานการณ์ที่กำหนดทดสอบ
- วัดเวลาทำงานสำเร็จ ข้อผิดพลาด และการส่งซ้ำก่อน/หลังเมื่อทดสอบกับเจ้าหน้าที่จริง ไม่แต่ง Baseline หรือตัวเลขเป้าหมายที่ไม่มีหลักฐาน

- Next.js App Router, Tailwind v4 และโครงสร้างปัจจุบันเป็นฐาน
